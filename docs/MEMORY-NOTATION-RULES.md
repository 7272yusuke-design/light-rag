# メモリ表記ルール v1.0

> **作成日**: 2026-05-10
> **目的**: Claude.aiユーザーメモリ更新時の表記ゆれによる混乱を防ぐ
> **背景**: 「未分類」と「未投入」を混同し、既投入エントリを再投入する事故を防ぐ

---

## 1. 状態を表す用語の定義

| 用語 | 意味 | 確認方法 |
|------|------|---------|
| **未投入** | LightRAG DBに**まだ無い** | `psql` で `file_path` 検索 → 0件 |
| **投入済み** | LightRAG DBに**既にある** | `psql` で `file_path` 検索 → 1件以上 |
| **未分類** | DBに**ある**が、レイヤー(L1/L2/L2c/L3)が確定していない | `file_path` にレイヤー接尾辞なし |
| **要昇格検討** | L2cとして投入済みで、L2に昇格できるか検討中 | `-l2c_` 接尾辞あり |
| **降格検討** | 現レイヤーが過大で、下位レイヤーへ移すか検討中 | 文脈による |

**最重要ルール: 「未分類」≠「未投入」**

ユーザーメモリで「未分類4件」と書いた場合、**それは投入済みでレイヤー未確定** という意味。
新規投入候補としてリストアップするときは必ず「**未投入**」と書く。

---

## 2. メモリ更新時のチェックリスト

新規ナレッジに言及する前に:

1. `file_path` で `psql` 検索して既存有無確認
2. 既存なら「投入済み」/「未分類」/「要昇格検討」のいずれか
3. 不在なら「未投入」
4. 用語を厳格に使い分け

---

## 3. 件数記載のルール

- 件数は**現実のDBクエリ結果**を書く(整合性チェックを兼ねる)
- 推測値や過去の値を流用しない
- 推奨フォーマット: `「2026-MM-DD時点・〜件、L3=X件、L2=Y件、L2c=Z件、L1=W件」`
- 整合性確認: `bash /docker/lightrag/scripts/inventory.sh` 実行 → 出力ヘッダの件数を転記

---

## 4. ファイル名表記のルール

- DBの `file_path` をそのまま書く(レイヤー接尾辞付き)
- 例: `agency-agents-msitarzewski-l3_lightrag.txt`
- 「agency-agents」のような短縮表記は混乱の元(同名複数あり得る)

---

## 5. 関連スクリプト

- 棚卸し: `bash /docker/lightrag/scripts/inventory.sh`
- 投入前チェック: `bash /docker/lightrag/scripts/pre-ingest-check.sh <ファイル>`

## 6. 同一URL複数エントリの判定基準

同じリポジトリ/URLから複数のナレッジエントリを作る**ことは許容される**。
ただし以下の条件を満たす必要がある。

### 6.1 許容されるケース（重複ではない）

- **観点(切り口)が明確に異なる**
  - 例: `comfyui-api-server-l3` (REST/WebSocket観点) と `comfyui-graph-execution-l3` (実行エンジン観点)
  - 例: `superpowers-workflow-l2` (概要・全体像) と `superpowers-full-l2` (個別スキル詳細)
- **タグが大きく異なる**(共通タグは1〜2個程度に留まる)
- **ファイル名にも観点が反映されている**(リポジトリ名+観点のサフィックス)
- **content先頭に「既存エントリとの関係」を明記**
  - 例: `## 既存ナレッジとの関係` セクションで補完関係を説明

### 6.2 重複(統合・削除すべきケース)

- 観点が同じ・タグが大半重複・ファイル名がほぼ同じ
- 投入時の認識ミスで同じ内容が2回入った(2026-05-04のagency-agentsケースなど)

### 6.3 投入時の判断手順

1. `pre-ingest-check.sh` でURL重複WARNが出る
2. 既存エントリを `psql` で確認(タグ・観点)
3. **観点が違う** → 投入OK、ファイル名に観点を含める、content先頭に関係性を記載
4. **観点が同じ** → 既存エントリの更新で対応(新規投入NG)
