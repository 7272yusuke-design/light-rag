# データスキーマ設計: ナレッジ構造化ルール

## 設計方針

1. 検索精度 > 網羅性 — 曖昧な情報より、正確で再利用可能な単位を優先
2. メタデータは投入時に付与 — 後から付けるのはコストが高い
3. 1ドキュメント = 1関心事 — 巨大なドキュメントは分割して投入
4. 鮮度は明示的に管理 — 投入日とソースの更新日を記録
5. カテゴリは固定、タグはLLM自由判定 — 大分類は人間が管理、小分類はLLMが付けて後から正規化

---

## ナレッジカテゴリ（固定・大分類）

LLMが自動判定する際、以下から1つ選択する。

### ドメインカテゴリ

| カテゴリ | 説明 | 例 |
|---|---|---|
| framework | フレームワーク・ライブラリの設計思想と使い方 | CrewAI, LangChain, FastAPI, Next.js |
| pattern | 実装パターン・アーキテクチャパターン | マルチエージェント, Pub/Sub, RAG, MVC |
| tool | ツール・CLI・開発支援の使い方 | Docker, git, Claude Code SKILL, Repomix |
| protocol | プロトコル・API仕様 | Virtual Protocol, OpenRouter API, MCP |
| infra | インフラ・デプロイ・運用 | VPS設定, PostgreSQL, Nginx, CI/CD |
| crypto | 仮想通貨・DeFi固有の知識 | DEX, トークン発行, ウォレット連携 |

### 開発領域カテゴリ

| カテゴリ | 説明 | 例 |
|---|---|---|
| website | Webサイト構築（静的・動的・デザイン） | LP, アニメーション, レスポンシブ |
| webapp | Webアプリケーション開発 | 認証, DB設計, API設計, ダッシュボード |
| agent | AI エージェント・自律システム | マルチエージェント, ツール連携, 推論ループ |
| workflow | ワークフロー自動化 | n8n, Make, 自動化パイプライン |

注: 1つのリポジトリが複数カテゴリに該当する場合、最も主要な1つをcategoryに、残りをsub_categoriesに入れる。

## タグ運用ルール

### LLM自動タグ付けの指針

LLMは要約時に3〜8個のタグを自由に付与する。ただし以下のルールに従う：

必須タグ:
- 言語タグ（python, typescript, rust など）

推奨タグ:
- ドメインタグ（trading, agent, web3, animation など）
- パターンタグ（multi-agent, rag, pipeline, scroll-effect など）
- 技術タグ（react, nextjs, fastapi, framer-motion など）

禁止:
- 汎用的すぎるタグ（code, development, programming）
- 3単語以上のタグ（multi-agent-orchestration-pattern → multi-agent）
- カテゴリ名と同一のタグ（frameworkをタグとして使わない）

### タグ正規化ルール（normalize_tags.py で自動適用）

全タグは小文字に統一。以下のエイリアスは正規形にマージ：

| 正規化前 | 正規化後 |
|---|---|
| nextjs, next.js, Next | nextjs |
| react, React.js, reactjs | react |
| multi-agent, multiagent | multi-agent |
| TypeScript, Typescript | typescript |
| MCP, model-context-protocol | mcp |
| RAG | rag |
| LLM | llm |
| FastAPI | fastapi |
| Docker | docker |
| SQLite | sqlite |

## 鮮度管理ルール

| status | 意味 | アクション |
|---|---|---|
| active | 最新で正確 | そのまま利用可 |
| review-needed | 180日以上更新なし | 再取得・再要約を検討 |
| outdated | 明確に古い情報 | 検索結果に含めるが警告を表示 |

自動チェック: check_freshness.py で投入日から180日経過を検出。--fixで自動的に review-needed へ遷移。

## ドキュメント分割ルール

LightRAGのエンティティ抽出精度を保つため：

- 1ドキュメント 3000文字目安以下（日本語の場合）
- 巨大リポジトリは「概要」「主要コンポーネント詳細」「実装パターン集」に分割
- 分割時はドキュメント名にサフィックスを付与（例: crewai-overview, crewai-patterns）

---

## 注意事項

- agency-agentsのようなYAML形式のエージェント定義ファイルはLightRAGのテンプレートに沿わないため投入しない
- 巨大リポジトリ（10M tokens超）はrepomixで0.2%程度しか使えないため、graphifyで事前に構造把握してから重要部分を特定する
- LightRAGは重複排除の自動検知機能あり（同一内容の再投入はスキップされる）

## ナレッジ3レイヤー定義

| レイヤー | 意味 | 内容 | ファイル名規約 |
|---------|------|------|--------------|
| L3 | 「作り方を知る」 | リポジトリ/ツール/スキルの実装知識 | `*-l3_lightrag.txt` |
| L2 | 「組み合わせ方を知る」 | パターン/手法論（複数L3の接続） | `*-l2_lightrag.txt` |
| L1 | 「状況を知る」 | プロジェクト固有/ドメイン知識 | `*-l1_lightrag.txt` |

### 投入ルール
- **L3**: 最初からL3品質で投入する。L1で入れてからL3に上げる方式は禁止（重複の原因）
- **L2**: 実装・動作確認済みのパターンのみ投入。未検証のアイデアは投入しない
- **L1**: プロジェクト固有の文脈情報。鮮度が最重要（6ヶ月で要レビュー）
- **削除**: DELETE API禁止（全消しバグ）。PostgreSQL直接操作（psql）で行う。操作前にpg_dump必須

### L3必須要素
- 概要（1-2文）
- インストール・セットアップ
- API / 主要インターフェース（引数・戻り値・エラーハンドリング）
- コード例 3件以上（基本・応用・エッジケース）
- ベストプラクティス
- アンチパターン
- 既存ナレッジとの接続

### L2必須要素
- 解決する課題
- 適用条件（いつ使う / いつ使わない）
- 使用するL3ナレッジ一覧
- アーキテクチャ / データフロー
- 接続コード（動作確認済み）
- 判明した制約・工夫
- 再利用条件

### L1必須要素
- プロジェクト概要・目的
- 制約条件・前提
- 関連するL2/L3ナレッジへの参照
- 最終確認日（鮮度管理）

## L2候補（L2c）レイヤー ※2026-04-18 追加

### 位置付け

L2（検証済みパターン）とは別の、**ブレスト・OSS読解ベースの未検証パターン**を蓄積するレイヤー。設計出力時の「着想の材料」として使う。

### L2とL2cの違い

| 区分 | L2（検証済み） | L2c（候補） |
|---|---|---|
| 投入条件 | 自分で実装・動作確認済み | ブレスト/OSS読解で「使えそう」と判断 |
| ファイル名 | `*-l2_lightrag.txt` | `*-l2c_lightrag.txt` |
| status | `active` | `unverified` |
| 用途 | 設計の「骨格」（動く前提で組み込める） | 設計の「着想」（方向性のヒント） |
| combination-architectでの扱い | そのまま提案に組み込み | 採用時は「未検証」と明示、検証TODO追加 |

### L2c投入条件（以下のどれか）

1. OSS読解で見つけた設計パターン
2. ブレストで「これは使えそう」と言語化できたアイデア
3. 複数のL3を組み合わせて思いついた新しい設計
4. 案件相談中に生まれた仮の設計案

### L2c必須要素（最小セット）

ブレストの勢いを殺さない最小限の型:

- パターン名（1行で言える）
- 解決する課題（なぜこのパターンが必要か）
- 参照するL3（最低1つ）
- 出典（OSS名 / 自分のブレスト / 案件xx）
- 未検証マーカー（status: unverified）
- 昇格条件（ビジネスイベント形式で具体的に）

### L2c昇格フロー（L2c → L2）

1. L2cパターンを自環境で実装・動作確認
2. L2cドキュメントに「検証結果」「判明した制約・工夫」を追記
3. ファイル名を `-l2c_` → `-l2_` にリネーム
4. KNOWLEDGE-DECISIONS.mdに昇格ログを記載
5. status: unverified → active に変更

### L2c鮮度管理

- 半年（180日）以上検証されないL2cは status: review-needed に遷移
- 1年以上放置されたL2cは削除候補（psql経由で削除）

## ナレッジ投入の判断フロー ※2026-04-18 追加

### 投入経路

| 対象 | 経路 |
|---|---|
| ナレッジ本体（L3/L2/L2c/L1） | Claude.ai LightRAGプロジェクトから upload_document |
| 管理ドキュメント（INDEX/DECISIONS/RESUME/SCHEMA等） | VPS上 /docker/lightrag/docs/ で直接編集 |

### ドメイン境界

- 汎用スキル・パターンのみLightRAGに投入
- 顧客固有情報（認証情報・仕様書・進捗）はClaude Code側で完結
- 自動収集は行わない（手動投入のみ）

### 4つの判断カテゴリ

新しいリソース（リポジトリ/ツール/パターン）評価時の判断:

| カテゴリ | 意味 | 再検討条件の書き方 |
|---|---|---|
| L3投入 | 実装ナレッジとして蓄積 | — |
| L2c投入 | 候補パターンとして蓄積、検証後にL2昇格 | 昇格トリガーをビジネスイベント形式で |
| 保留 | 領域は合うが時期尚早 | フェーズ進展トリガー（例: OpenClaw本格化時） |
| 見送り | 現在のビジネス領域から外れる | 領域進出トリガー（例: 電子署名案件受注時） |

### 再検討条件の書き方ルール

- ❌ 「案件時」「実装時」（漠然・禁止）
- ✅ 「OpenClaw本格化時」「電子署名案件受注時」「n8n→アプリ開発アップセル成立時」（具体ビジネスイベント）

### 判断ログの記録先

- 投入・L2c・保留・見送りの全判断を KNOWLEDGE-DECISIONS.md に記録
- 再評価時は必ずDECISIONSを参照して重複判断を避ける
- DECISIONSの項目: 対象名 / 判断 / 理由 / 日付 / 再検討条件 / 出典URL

### 投入前の必須チェック

1. **重複チェック**: search_knowledge で既存ナレッジと被らないか確認
2. **境界チェック**: 汎用か？ 顧客固有情報を含まないか？
3. **判断確定**: 4つのカテゴリのどれか決定
4. **DECISIONS記録**: 判断結果をKNOWLEDGE-DECISIONS.mdに追記

## L1再定義 ※2026-04-18 v3追加

### 背景

初期のL1定義「プロジェクト固有/ドメイン知識」は、実運用で以下の問題を起こしていた:

1. プロジェクト進捗・仕様書・ペルソナがLightRAGに蓄積され、検索ノイズ化
2. Claude.aiプロジェクト側・Notion等と情報が重複
3. 低優先プロジェクトのL1が放置され、鮮度管理が機能せず
4. 発信用途で顧客固有情報が混入するリスク

活用目的を逆算すると、L1に残すべきは「L2/L3を正しく使うための前提」のみと判明。

### L1の新しい役割

L2/L3を参照する際の**横断運用のメタ知識**および**環境前提**。
プロジェクト固有情報はLightRAGに投入しない（Claude.aiプロジェクト/プロジェクト管理ツールで管理）。

### L1のサブタイプ

| サブタイプ | 内容 | 例 |
|---|---|---|
| L1-Infra | 開発環境・インフラの横断的前提 | VPS構成、DB接続設定、CLIツール運用、Hostinger特性 |
| L1-Ops | LightRAG運用自体のメタ知識 | ナレッジ投入ルール運用知見、psql削除手順、pg_dump運用 |

### L1投入条件

以下の全てを満たすものだけL1投入:

1. 複数プロジェクトで再利用される知識である
2. 顧客固有情報・進捗情報・ペルソナを含まない
3. L2/L3の参照時に文脈として必要になる

### L1から外すもの（v3で除外決定）

- 特定プロジェクトの進捗・仕様書 → Claude.aiプロジェクトまたはNotion
- ペルソナ・個人設定 → Claude.aiプロジェクトメモリ
- 案件固有の実装詳細 → 汎用化してからL2cへ
- 低優先プロジェクトのコンテキスト → LightRAG外（または削除）
- 旧・残骸 → 削除

### L1→L2c昇格フロー

案件完了時、L1から以下を抽出してL2cへ昇格可能:

1. 汎用化できる手法論
2. 他プロジェクトで再利用できる設計判断
3. 複数プロジェクトで観察されたアーキテクチャパターン

昇格手順:
- L1の該当部分を抽出し、L2cテンプレートで新規ドキュメント化
- ファイル名: `*-l2c_lightrag.txt`
- 元のL1ドキュメントから該当記述を削除
- KNOWLEDGE-DECISIONS.mdに昇格ログを記載

### L1鮮度管理

- L1-Infra / L1-Ops とも6ヶ月で要レビュー（status: review-needed）
- プロジェクト情報を含むL1は**v3移行で全件見直し対象**
- レビュー時は「現在も複数プロジェクトで再利用されているか」を基準に判断

### ファイル名規約

| サブタイプ | ファイル名 | 例 |
|---|---|---|

### L2の品質ゲート強化（v3で追加）

L2へのプロジェクト固有情報の混入を防ぐため、以下をL2の必須要件に追加:
